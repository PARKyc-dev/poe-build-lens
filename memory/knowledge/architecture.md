# Architecture

## Browser PoB Analysis

PoB 내보내기 코드와 `pobb.in` 입력은 브라우저 `Web Worker`에서 원본 PoB `HeadlessWrapper.lua`로 처리한다. React는 계산 결과를 사용해 빌드 인사이트와 상세 화면을 렌더링한다.

PoB 원본 버전 고정, 가져오기, 캐시와 자산 생성 입력은 `web/pob/`에서 관리한다. 이 저장소가 소유하는 Lua/WebAssembly 호스트와 자산 패커를 사용하며, `pob.cool`은 이식 기법을 검토하는 참고 구현체일 뿐 제품 런타임·자산·업데이트 의존성에는 포함하지 않는다.

상세 화면의 `스킬젬 상세`은 `buildFacts.skills`의 활성 스킬을 그룹 기준으로 사용하고, 각 스킬의 활성 `supports`를 실제 연결된 보조 젬으로 표시한다. 그룹은 주력 공격, 보조 공격, 방어·가드, 오라·버프, 이동기, 유틸리티, 자동 발동 순으로 정렬하며 같은 분류에서는 PoB 순서를 유지한다.

PoB의 Hex는 `buildFacts.buffs.kind=curse`, Mark는 `kind=mark`로 구분한다. 적 대상 저주·징표는 플레이어 `buffList`에 없을 수 있으므로 활성 스킬의 `SkillType.Hex`와 `SkillType.Mark`에서도 직접 추출한다. 두 종류 모두 방어 관련 태그가 있어도 방어·버프 기재와 분리해 `저주/징표 기재`에 표시하고, 연결된 AI 버프 설명도 제목의 대상 이름을 기준으로 같은 영역으로 이동한다.

`worker/`는 향후 확장을 위한 예약 영역이다. 현재 브라우저 Web Worker와 혼동하지 않는다.

## 공격 메커니즘 설명

- 공격 후보는 PoB에서 선택한 공격 스킬을 우선하고 나머지 후보는 DPS 순으로 선택한다. 이 순위로 맵핑·보스 역할을 단정하지 않는다.
- `buildFacts.skills`는 PoB가 계산한 활성 스킬과 실제 적용 가능한 보조 효과를 전달한다. `effects`는 실제 레벨·퀄리티를 반영한 설명이며, 보조젬의 적용 대상 소개 문구와 구분한다. 이동기 연결도 공격의 비용·버프 관계 분석 근거로 사용한다.
- `buildFacts.conditions`는 버프·정지·충전 등 PoB 계산 가정이다. 실제 전투에서 자동·상시 충족되는 조건으로 해석하지 않는다. 장비 근거에는 고정 속성과 명시 속성을 모두 포함한다.
- AI 공격 설명은 동작 과정과 핵심 상호작용 중심이다. 응답 스키마가 공격 이름과 출처 이름을 실제 빌드의 목록으로 제한하고 서버가 출처 및 흐름 연결을 검증한다. 검증은 출처 식별자를 확인하며 문장의 모든 인과관계를 증명하지는 않는다.
- 공격 섹션의 attackName은 별도 필드로 검증하므로 evidence에 중복할 필요가 없다. 방어 섹션은 실제 PoB defenceKind만 사용할 수 있고 설명에 사용한 빌드 출처를 evidence로 함께 기록할 수 있으며, 중요하지 않은 방어 수치까지 모두 섹션으로 만들 필요는 없다.
- 원소·카오스 저항은 개별 방어 섹션 대신 `resistances`의 `저항 체계`로 통합한다. 저항 적용 방식·최대치·피해 전환을 바꾸는 근거가 있을 때만 `resistance-interaction`의 `저항 핵심 상호작용`을 추가한다. 설명 속 전직 노드는 PoB 전체 이름을 사용하며 웹에서 주황색으로 강조하고, hover 또는 키보드 focus 시 전직 효과 팝업을 표시한다.
- 저항 섹션의 evidence에서는 합성 식별자 `resistances`와 `resistance-interaction`을 각자 해당 섹션의 구조 표식으로 허용한다. 나머지 evidence는 실제 PoB 출처여야 하며, 같은 저항 제목으로 여러 문단이 생성되면 검증 후 한 항목으로 병합한다.
- 방어 섹션은 defenceKind를 별도 필드에서 검증한다. evidence는 한 섹션의 defenceKind로 한정하지 않고 빌드에 존재하는 전체 방어 사실, 버프 태그, 실제 출처와 허용된 구조 식별자를 사용할 수 있으며 OpenAI 응답 스키마도 같은 목록으로 제한한다.
- 공격·방어·버프 분석 대상이 없으면 해당 OpenAI 응답 배열은 스키마에서 빈 배열로 강제한다. 대상 식별자는 실제 PoB 목록으로 제한하고 evidence는 PoB 전체의 검증된 출처를 사용할 수 있다. 선택적 대상 누락은 허용하되 존재하지 않는 대상이나 근거는 거부한다.
- OpenAI strict Structured Outputs의 빈 배열도 `maxItems: 0`과 함께 완전한 item 객체 스키마를 사용한다. 모든 item 객체는 properties의 전체 필드를 required로 지정하고 `additionalProperties: false`를 설정한다.
- 빌드 요약과 공격·방어·버프 설명은 AI만 생성한다. 서버 규칙은 PoB 사실에서 운용 흐름을 추출하고 AI 응답의 출처·섹션을 검증하는 데만 사용한다.
- `buildSummary`는 수치와 상세 출처를 제외한 3~5문장의 핵심 작동 구조만 담는다. 구체적인 공격 동작·수치·상호작용, 방어 수치·조건, 버프 효과·유지 조건은 해당 상세 섹션에 둔다.
- AI 실패 시 내부 수정자 나열이나 규칙 기반 설명을 반환하지 않고 상세 설명 생성 실패를 알린다. HTTP 제한은 90초, 대기 제한은 95초이며 대기 실패 시 작업을 취소한다.

## OpenAI 호출 제한

- API 운영 데이터베이스는 PostgreSQL이며 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 반드시 설정한다. H2는 자동화 테스트에서만 사용한다.
- 실제 OpenAI 요청 직전에 Supabase PostgreSQL의 `openai_daily_usage`를 원자적으로 증가시킨다. 서비스 전체 기준 Asia/Seoul 날짜별 100회까지 허용한다.
- `/api/ai-usage`는 오늘자 사용량과 `poe-lens.openai.daily-limit` 설정값을 반환한다. 웹 메인 화면은 이 응답을 `사용량/한도` 형식으로 표시하고 분석 시도 후 갱신한다.
- 일일 한도를 넘으면 HTTP 429 `AI_DAILY_LIMIT_REACHED`를 반환하고 웹은 금일 리미트 도달 알림을 표시한다.
- OpenAI가 비활성화됐거나 호출·응답 검증·사용량 저장이 실패하면 규칙 기반 문장을 대신 반환하지 않고 `AI_GENERATION_FAILED` 오류를 반환한다.
